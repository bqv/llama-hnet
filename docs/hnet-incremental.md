# Incremental H-Net decoding

Today every generated byte re-encodes the whole prefix: `hnet-generate` calls `llama_encode` then `llama_decode`
on the full sequence each step. That is O(n^2) and it is the main reason generation is slow even at Q4.

This note records what has to exist before that loop can become a real decode step, and in what order to build it.

## The three states

| state | shape | producer | consumer |
|---|---|---|---|
| encoder Mamba-2 conv + SSM | per enc layer: `d_conv-1` x `conv_dim`, and `d_state` x `d_head` x `n_head` | graph A | next graph A |
| router previous hidden | `d_enc` | graph A | next router |
| main-stack attention KV | per main layer, per head: `d_head` x `2` per chunk | graph B | next graph B |
| de-chunk EMA | `d_enc` | graph B | next graph B |
| decoder Mamba-2 conv + SSM | as encoder | graph B | next graph B |

The first row is what llama.cpp already knows how to cache: `llama_memory_recurrent` stores conv and SSM state per
layer and is what `mamba-base.cpp` uses through `build_rs`. Our `create_memory()` currently returns a layer-less
recurrent memory purely to satisfy the decode guard, and the mamba layer builder passes zero state.

## What changes

1. **Memory**: allocate `n_enc + n_dec` recurrent layers, each with the shapes from `hnet_mamba2_get_dims`. The
   main transformer needs a separate KV cache keyed by chunk position, not byte position.
2. **Encoder layer**: replace the zero-state `ggml_ssm_scan` with one that reads and writes the recurrent state,
   exactly as `mamba-base.cpp` does (`build_rs`, then scan with the state views).
3. **Router**: needs the previous hidden state. One row of `d_enc` per sequence, kept in the context, written by
   graph A and read by the next call. This is the cheapest piece.
4. **Chunk gather**: with one new byte per step, the number of new chunks per step is 0 or 1. So graph B is only
   needed when the router emits a boundary - otherwise the new byte's decoder output is produced from the current
   EMA and the previous chunk state, with no main-stack work at all.
5. **De-chunk**: the EMA value per sequence becomes state; the new byte's output is `(1-cp) * ema + cp * h`, or
   `(1-cp) * ema + cp * h_new` when a chunk ended.

## Order of work, each step independently testable

1. Router previous-hidden state (cheapest, and it removes one full encoder pass per step from the correctness
   argument).
2. Recurrent state for the encoder and decoder layers via `llama_memory_recurrent`, verified by comparing the
   last-byte hidden state against a full re-encode on a 24-byte prompt.
3. KV cache for the main stack over chunk positions.
4. Replace the re-encode loop in `hnet-generate` with a single `llama_decode` per byte, and cross-check the first
   32 generated bytes against the current implementation, byte for byte.

Step 4 is the acceptance test: identical bytes, much faster. Everything before it can ship without changing
observable behaviour, which is why the parity fixture stays useful throughout.

## Why the first three attempts failed

Three attempts to bolt recurrent state onto the existing graph functions segfaulted at run time. The common cause
was not the state maths: it was the tensor layout. The upstream mamba-2 builder assumes three dimensions with an
explicit `n_seqs` axis (`{d_conv-1, conv_dim, n_seqs}`, `{d_state, head_dim, n_head, n_seqs}`, scan rows indexed by
`ids`), and our graphs build two-dimensional tensors `{width, n_tokens}` with the sequence dimension implied. Every
port so far has been an adaptation of 3-D code to 2-D tensors, and each adaptation has produced a view or a cpy
whose extents do not match.

The next attempt should stop adapting: build the hnet encoder and decoder tensors as 3-D `{width, n_tokens, 1}`,
pass `n_seqs = 1`, and copy the upstream builder almost verbatim. That way the shapes the code assumes are the
shapes the graph has.

The fourth attempt narrowed it further. With a memory context finally passed to `process_ubatch` for the encoder
graph, the crash moved into `build_rs_inp_impl`, in `ggml_view_1d(ctx0, inp->s_copy, n_rs - 1, ...)`: `n_rs` is zero
for the encoder batch, so `n_rs - 1` underflows and the view is rejected. `get_n_rs()` reports the number of sequence
rows the memory context reserved, and `memory->init_batch(*balloc, cparams.n_ubatch, true)` in the encoder path
appears to reserve none, unlike the decode path where the same call reports one. That is the concrete next thing to
understand: why `init_batch` yields zero sequence rows for the encoder ubatch.

Probing the encoder path directly answers the `n_rs` question and replaces it with a different one: `init_batch`
succeeds and the memory context reserves one sequence row (`n_rs = 1`), but the ubatch handed to `process_ubatch`
reports `n_seqs = 23` for a 23-token, single-sequence batch. `build_rs_inp_impl` then sizes `s_copy_main` from
`ubatch.n_seqs` (23) inside an `s_copy` sized by `n_rs` (1), which is exactly the bounds assert.

The cause is `balloc->split_simple(n_tokens)` in `encode()`: `split_simple` calls `ubatch_add(idxs, idxs.size(), false)`,
i.e. it reports one sequence per token by construction. Calling `split_equal(n_tokens, true, 0)` instead makes
`ubatch.n_seqs` 1 for a 23-token single-sequence batch, which was verified.

So the remaining defect is the sequence count on the encode path: the encode batch is being expanded to one
sequence per token somewhere between the caller and `process_ubatch`, while the memory module correctly sees one.
That is the thing to fix next, and it is a caller-side batch-construction issue rather than a state-graph issue.

With `split_equal` in place and conv state wired through `build_rs`/`build_conv_state_store`, `hnet-segment`
produced the correct boundaries, but `hnet-decode` then failed (`decode rc = -1`), most likely because the encoder
now leaves recurrent state committed and the decode batch's `balloc` sees non-consecutive positions. Both changes
were reverted together; the next attempt should keep the encoder's memory context private to the encoder pass
(or clear it before decode) rather than sharing one cell across the two passes.

Also fixed along the way: `create_memory()` passed a layer filter returning false, so the recurrent memory skipped
every layer and the state accessors were null for all indices. That was the cause of the first two failures.

## Blocker to be aware of

The main stack currently has no KV cache and runs `n_tokens` rows instead of `n_chunk` rows. Attempting to size it
by chunk count alone aborts in `ggml_concat` because a downstream tensor is still byte-sized; both changes have to
land together, so items 3 and the row-count cleanup are one piece of work rather than two.
